# ISTQB Chapter 1 Glossary

This table helps you quickly confirm each term and its meaning.

| Term | Meaning |
|---|---|
| Acceptance criteria | Conditions that a product or feature must satisfy to be accepted by stakeholders. |
| Activity | A task or step in the testing process. |
| Bug | A defect in the software. |
| Business goal | A desired outcome of the product from the business perspective. |
| Confidence | The level of trust stakeholders have in the quality of the software. |
| Context | The environment or situation in which testing is performed. |
| Coverage | The extent to which a test basis or requirement has been exercised by tests. |
| Coverage item | An item that must be covered by a test. |
| Debugging | The process of finding, analyzing, and fixing the cause of a failure. |
| Defect | A flaw in a component or work product that can cause the software to fail. |
| Defect clustering | The tendency for defects to appear in a small number of areas. |
| Dynamic testing | Testing that involves executing the software. |
| Error | A human mistake that introduces a defect. |
| Evaluation | The process of assessing work products or software quality. |
| Exhaustive testing | Testing every possible case; usually impractical. |
| Failure | An observed incorrect behavior of the software during execution. |
| Fault | Another word for defect. |
| Functional requirement | A requirement describing what the system should do. |
| Governance | The framework and rules used to control and guide work. |
| Independence of testing | A level of separation between the person who creates the work product and the person who tests it. |
| Iterative | Repeated in cycles. |
| Legal requirement | A rule or law that the software must comply with. |
| Lesson learned | A useful insight gathered after completing activities, for improvement in future work. |
| Methodical | Done in an organized and systematic way. |
| Monitoring | Checking progress and comparing it to the plan. |
| Objective | A goal or purpose. |
| Operational environment | The real-world environment in which the software is used. |
| Pareto principle | The idea that a small number of causes often produce most of the effects. |
| Prevention | Taking action to avoid problems before they happen. |
| Product backlog | A list of work items or features to be developed. |
| Project milestone | A key point in a project timeline. |
| Quality | The degree to which a product satisfies requirements and meets stakeholder needs. |
| Quality assurance (QA) | A process-oriented, preventive approach to ensure quality. |
| Quality control | A product-oriented, corrective approach that includes testing. |
| Regression testing | Testing done to confirm that previous defects remain fixed and new defects were not introduced. |
| Requirement | A need, expectation, or condition that the software must fulfill. |
| Risk | The possibility of an undesirable event or outcome. |
| Root cause | The underlying reason for a defect or failure. |
| Root cause analysis | The process of identifying the main cause of a problem. |
| Stakeholder | A person or group interested in the software and its outcome. |
| Static testing | Testing that does not execute the software, such as reviews and static analysis. |
| System thinking | Considering the whole system and how its parts interact. |
| Test analysis | The activity of studying the test basis and identifying test conditions. |
| Test basis | The source information used to derive test cases, such as requirements and design documents. |
| Test case | A set of input values, execution conditions, and expected results. |
| Test completion | The final stage of testing at a milestone or release. |
| Test condition | A specific aspect of the test object that can be tested. |
| Test control | Actions taken to ensure the test objectives are met. |
| Test data | Data used as input for testing. |
| Test design | The process of turning test conditions into test cases and related testware. |
| Test environment | The hardware, software, network, and tools needed to run tests. |
| Test execution | Running the tests and comparing actual results with expected results. |
| Test implementation | Preparing the testware needed for test execution. |
| Test log | A record of the details of a test run. |
| Test monitoring | Measuring progress and comparing it to the test plan. |
| Test object | The work product being tested. |
| Test objective | The goal of testing in a particular context. |
| Test planning | Defining the strategy, approach, and scope of testing. |
| Test procedure | A sequence of steps for executing tests. |
| Test process | The set of test activities and tasks used to achieve test objectives. |
| Test result | The outcome of executing a test. |
| Test suite | A group of test cases or procedures. |
| Testware | All work products produced during testing, such as test cases, scripts, and logs. |
| Testing | A set of activities to discover defects and evaluate the quality of software work products. |
| Traceability | The ability to connect test basis elements, test cases, results, and defects. |
| Validation | Checking whether the software meets the needs and expectations of users and stakeholders. |
| Verification | Checking whether the software satisfies specified requirements. |
| Work product | Any artifact produced during the software lifecycle, such as requirements, design documents, code, or test cases. |

## Quick study tip

Try to remember these three groups:
- Quality and defects: quality, defect, failure, root cause
- Testing activities: planning, analysis, design, implementation, execution, completion
- Testing mindset: verification, validation, traceability, independence
