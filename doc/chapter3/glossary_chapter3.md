# ISTQB Chapter 3 Glossary

This glossary explains the key ideas in Chapter 3 in a more practical and easy-to-understand way.

## 1. Static Testing Basics
- Static testing: Testing that does not execute the software. It is performed by examining work products such as requirements, designs, code, or test cases.
- Why it matters: Static testing helps find defects early, before the system is run.
- Example: Reviewing a requirement document before coding starts.
- Dynamic testing: Testing that executes the software to observe its behavior.
- Key difference: Static testing checks the product without running it; dynamic testing checks it by running it.

## 2. Work Products Examined by Static Testing
- Work product: Any output created during the software lifecycle, such as requirements, design documents, code, or test cases.
- Examples of work products that can be reviewed:
  - requirements specifications
  - user stories and acceptance criteria
  - architecture and design documents
  - source code
  - test cases and test plans

## 3. Value of Static Testing
- Early defect detection: Defects can be found before they become expensive to fix.
- Cost reduction: Fixing issues early usually costs less than fixing them later.
- Better quality: Review and analysis improve the clarity and correctness of work products.
- Faster learning: Team members understand the work product more deeply through review.

## 4. Review Process
- Review: A structured or semi-structured activity where work products are examined by others to find defects or improvements.
- Review process activities usually include:
  - planning the review
  - preparing the work product
  - examining the work product
  - collecting feedback
  - making improvements
- Benefit: Reviews support communication and improve quality.

## 5. Review Types
- Informal review: A simple, less structured review with fewer formal rules.
  - Example: A teammate quickly checks a requirement document.
- Walkthrough: The author explains the work product to others so they can provide feedback.
- Technical review: A review focused on technical correctness and quality.
- Inspection: A formal review process with defined roles, rules, and outputs.
  - Example: A formal review of a design document with a checklist and review record.

## 6. Roles in Reviews
- Author: The person who created the work product.
- Reviewer: The person who examines the work product for defects or issues.
- Moderator: The person who coordinates the review process.
- Scribe: The person who records issues and decisions during the review.
- Why roles matter: Clear roles help reviews be more effective and organized.

## 7. Success Factors for Reviews
- Clear objectives: Everyone should know why the review is being done.
- Good preparation: Reviewers need enough time to understand the work product.
- Skilled participants: Reviewers should have the right knowledge and experience.
- Constructive communication: Feedback should help improve the work product, not blame people.
- Appropriate review type: The review method should match the importance and complexity of the work product.

## 8. Static Analysis
- Static analysis: An automated way to analyze code or documents without executing the software.
- Example: A linter detecting coding issues or a tool scanning for security vulnerabilities.

## 9. Anomaly
- Anomaly: An unusual condition or issue found in a work product.
- In review terms, an anomaly may be a defect, risk, or something that needs clarification.

## Quick memory tip
- Remember this: static testing = review and analysis before execution.
- If you remember one sentence, remember: early reviews save time and reduce cost.
