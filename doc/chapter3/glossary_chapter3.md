# ISTQB Chapter 3 Glossary

This table gives you a quick overview of the key terms in Chapter 3.

| Term | Meaning |
|---|---|
| Static testing | Testing that does not execute the software; it examines work products such as requirements, code, or test cases. |
| Dynamic testing | Testing that executes the software to observe its behavior. |
| Work product | Any output created during the software lifecycle, such as requirements, design documents, code, or test cases. |
| Early defect detection | Finding defects before they become expensive to fix. |
| Cost reduction | Fixing issues early usually costs less than fixing them later. |
| Better quality | Review and analysis improve the clarity and correctness of work products. |
| Review | A structured or semi-structured activity where work products are examined by others. |
| Informal review | A simple, less structured review with fewer formal rules. |
| Walkthrough | The author explains the work product to others so they can provide feedback. |
| Technical review | A review focused on technical correctness and quality. |
| Inspection | A formal review process with defined roles, rules, and outputs. |
| Author | The person who created the work product. |
| Reviewer | The person who examines the work product for defects or issues. |
| Moderator | The person who coordinates the review process. |
| Scribe | The person who records issues and decisions during the review. |
| Static analysis | An automated way to analyze code or documents without executing the software. |
| Anomaly | An unusual condition or issue found in a work product. |
| **Static testing**         | Testing of a work product without execution of the software. Includes reviews and static analysis. |
| **Dynamic testing**        | Testing that involves the execution of the software / component / system. |
| **Work product**           | Any artifact produced during the software development lifecycle (requirements, design, code, test cases, documentation, etc.). |
| **Review**                 | A type of static testing where a work product is examined by one or more persons to detect defects. |
| **Informal review**        | A review that does not follow a defined process and has no formal documented output. |
| **Walkthrough**            | A review in which the author of the work product leads the participants through the product and the participants ask questions and make comments. |
| **Technical review**       | A formal review technique that focuses on the technical content and quality of the work product. |
| **Inspection**             | A formal review technique characterized by defined roles, a documented process, metrics collection, and formal documented output. |
| **Author**                 | The person who created the work product under review. |
| **Reviewer**               | A participant in a review who identifies potential defects in the work product. |
| **Moderator / Facilitator**| The person who leads the review process and ensures that the review is conducted effectively. |
| **Scribe / Recorder**      | The person who records issues, defects, and decisions during a review meeting. |
| **Static analysis**        | Analysis of work products (usually code or models) performed by tools without execution of the software. |
| **Anomaly**                | Any condition that differs from expectations (potential defect found during review or static analysis). |
| **Early defect detection** | Finding defects as early as possible in the lifecycle, which significantly reduces the cost of fixing them. |
| **Success factors for reviews** | Conditions that increase the effectiveness of reviews (clear objectives, proper preparation, good moderation, management support, blame-free culture, etc.). |

## Quick memory tip

Remember this: static testing = review and analysis before execution.
